# 洗錢防制客戶風險評估系統

保險經紀人公司專用。業務人員於招攬時以手機完成客戶風險辨識評估，資料即時回到公司，
洗錢防制專責人員隨時監控，並可匯出董事會定期報告與年度主管機關申報報表。

## 法規依據

| 依據 | 系統對應 |
|---|---|
| 保險經紀人公司防制洗錢及打擊資恐、資助武擴注意事項範本（113.12.31 金管保綜字第1130436219號函備查） | 全系統 |
| 　第四點　應婉拒建立業務關係之情形 | 勾選任一項即**擋件**，業務員不得續辦 |
| 　第五點　風險基礎方法、高風險強化措施 | 強制高風險規則、主管同意流程、財富與資金來源必填 |
| 　第六點　紀錄保存 | 個資加密儲存、案件不實體刪除、保存期限欄位 |
| 　第九點　疑似洗錢交易申報 | 態樣勾選 → 專責待辦 → STR 標記與申報編號留存 |
| 　第十點　風險評估報告每年更新並送主管機關 | 年度報表匯出（115 年格式） |
| 　第十三點　員工訓練 | 帳號頁登錄完訓日，逾一年標示 |
| 內部控制制度手冊 BIC06-03 洗錢防制作業 | 風險評估、高風險管控、名單管理、董事會提報 |
| 內部控制制度手冊 BIC05-02 資訊安全作業 | 個資加密、角色權限、稽核軌跡、容器非 root 執行 |

## 評分模型

沿用現行紙本檢核表：**10 個風險因子、總分 10～48 分、30 分以上（含）為高風險**。

**業務人員不得知悉分數與風險等級。** 前台只顯示填答進度，選項旁不標示配分
（否則把 10 個數字加起來即可還原總分），區塊標題亦不揭露「勾了就是高風險」。
當作答結果跨越門檻或觸發強制規則時，畫面提示「本案須照會單位主管確認後方得建立業務關係」，
業務員須登錄照會之主管姓名，**送出鈕才會啟用**；該照會紀錄併入稽核軌跡。
分數與等級僅對單位主管、洗防專責、內部稽核與系統管理者揭露（`app/deps.py::can_see_score`）。

分數之外另有兩層硬規則，兩者都不受總分影響：

- **擋件（範本第四點）** — 命中制裁名單、持偽變造證件、無法辨識實質受益人等 10 項情形之一，
  系統標示「應婉拒建立業務關係」並鎖定案件。
- **強制高風險（範本第五點、附錄）** — PEP、高風險國家、所有權結構異常、媒體報導重大案件、
  曾申報 STR，以及 11 項疑似洗錢態樣。

此外，每次儲存客戶姓名、每次開啟案件、以及送出時，系統都會拿**要保人、被保險人、受益人**
三個姓名去比對名單。比對永遠使用當下的名單而不快取，因此名單更新後重新檢視舊案件，
仍會反映新名單的結果（`test_newly_added_list_entry_affects_existing_cases`）。

> **為什麼需要硬規則**：現行紙本純以總分判定，而「命中制裁名單」僅計 5 分。
> 一個制裁名單客戶其餘各項皆為最低分時總分僅 14 分，會被判為「一般風險」——
> 但依範本第四點，此情形本應婉拒建立業務關係。此缺口由 `test_sanction_list_hit_blocks_regardless_of_score` 鎖住。

問卷定義在 `app/scoring/definitions/life_v1.yaml`，**版本化**管理。
法規或內部制度修訂時請新增 `life_v2.yaml` 而非就地修改，既有案件才能以當時生效的版本重現評分。

## 名單比對

支援匯入完整制裁名單（xlsx／csv），實測 26,579 個對象、60,667 個可比對名稱，
匯入耗時約 19 秒，單次比對約 5 毫秒。後台「名單管理」上傳，或
`python -m scripts.import_sanctions <檔案>` 供每月例行更新。
狀態為「已除名」者匯入後自動停用，不再觸發警示。

### 比對方向是固定的

**名單上的名稱必須出現在客戶姓名之中，永不反向。** 這不是實作細節，是可用性的前提：
完整名單中有近千筆名稱短於五個字元（Joe、Adam、IZO、陳世憲）。若採雙向包含比對，
客戶姓「陳」會命中名單上的「陳世憲」，姓名含 Adam 者會命中 Adam ——
全公司客戶都會被標紅，警示疲乏後真正的命中反而被忽略。

作法是由客戶姓名（很短）產生候選字串，再以索引查詢名單（很長），不做全表掃描：

1. 整串正規化後的姓名 → 完全相符
2. 詞彙子集的排序鍵 → 拉丁字母姓名的詞序差異（CHEN SHIH-HSIEN／SHIH-HSIEN CHEN）
3. 連續子字串 → 名單名稱嵌在較長的公司名稱中（純漢字至少 3 字，其餘至少 6 字元）

長度下限只作用於子字串；客戶姓名整串一律做完全比對，因此客戶就叫 Adam 時仍會命中。
以 500 個真實台灣姓名與公司名實測，誤報 0 件。

| 命中強度 | 判定 | 處置 |
|---|---|---|
| 完全相符 | 客戶姓名整串等於名單上的名稱 | 制裁／資恐名單 → **擋件**；PEP → 強制高風險 |
| 部分相符 | 名單名稱為客戶姓名的一部分 | 強制高風險，須人工複核，不逕行擋件 |

分級的理由：範本第四點要求婉拒的是「對象為制裁名單所列者」，部分相符尚未構成該認定，
逕行擋件會誤傷同名同姓之人。

「高風險國家／地區」名單不參與姓名比對——拿國名比對客戶姓名沒有意義，
國別風險由問卷的地域與國籍因子及強制勾選題涵蓋。

### 命中留痕

一旦命中即寫入案件，**不因業務員事後修改姓名或放棄草稿而清除**。
沒有這道留痕，業務員看到「應婉拒」後只要放棄草稿、改個寫法重填，
洗防人員永遠不會知道曾經命中過。洗防儀表板獨立列出所有曾命中的案件，
並特別標示命中後停留在草稿逾 24 小時未送出者。

### 命中制裁／資恐名單者，送出後須經洗防覆核

擋件依「當下」的姓名判定，改個寫法即解除。留痕能讓洗防人員**看得到**，
但看不看、何時看，仍取決於人。因此曾命中制裁或資恐名單的案件，送出後
一律進入 `HIT_REVIEW`（待洗防覆核），不進入其後任何流程，直到洗防專責
作成結論並填列理由：

| 結論 | 後續 | 依據 |
|---|---|---|
| 確認為名單所列對象 | 婉拒建立業務關係，不排定期審查 | 範本第四點 |
| 同名誤判或姓名確經更正 | 回到原本應有的流程（高風險仍須主管同意） | — |

結論（何人、何時、憑什麼）寫入案件本身，金檢調閱時無須翻稽核軌跡即可查得。
PEP 命中不在此列——PEP 本就由強制高風險規則導向主管簽核，另設關卡只會製造
無謂的積案，反而稀釋制裁名單命中的重要性。

## 既有客戶的持續監督

招攬當下評估一次不足以滿足範本第五點第一款第三目之「強化之持續監督」與
問答集 Q8 之定期檢視要求。系統提供兩件事：

**批次重新篩檢**（自動，防護價值較高的一半）——名單每月更新，既有客戶可能事後才被列入。
以當下名單重新比對所有仍在監督中的案件，只標記先前未命中、現在命中者；
命中留痕沿用既有機制，結果直接出現在儀表板的命中清單。
由後台按鈕或 `python -m scripts.run_rescreen` 排程執行，建議每次名單匯入後執行。

**定期審查**（人工，法規要求）——送出時依風險等級排定應審查日
（高風險 12 個月、一般風險 36 個月，見 `config.review_months_*`），
到期由洗防專責複核並記錄結論：維持／調升／調降／應重新辦理客戶審查／終止業務關係。
調升會縮短下次週期，終止會結案並停止監督。每次審查寫入 `periodic_reviews` 保留完整歷程，
儀表板顯示逾期未審查件數。擋件案件不排審查——本就不得建立業務關係，沒有業務往來可監督。

## 業務端行為監控

隱藏分數大幅提高了湊分數的難度，但沒有完全消除：業務員仍看得到「須照會主管」的警示
隨作答出現與消失，反覆嘗試即可摸索出關鍵題目。因此第二道防線仍須看得見**作答過程**，
而不只是最終結果。

`/compliance/anomalies` 依唯增稽核軌跡（業務員無從修改）產生下列訊號：

- 作答過程中總分曾達門檻，最終卻降至一般風險
- 跨越門檻後逐步調降的每一個因子與前後分數
- 最終總分緊貼門檻下緣（27～29 分）
- 同一因子反覆改寫達 3 次以上
- 自首次作答至送出不足 90 秒（10 題涵蓋職業、資金來源、付款人，難認曾當面詢問）

## 上線前置作業

順序不可顛倒：組織單位必須先於名冊建立，否則名冊匯入會因單位代碼不存在而整批退回。

1. **建立組織單位**（通訊處／營運中心）— 決定主管的簽核範圍與報表的單位別分布。
2. **批次匯入業務員名冊** — `系統管理 → 批次匯入業務員名冊`，上傳 CSV（UTF-8 或 Big5）。
   欄位：帳號、姓名、角色、單位代碼、業務員登錄字號、登錄有效日期、洗防訓練完訓日；
   帳號與姓名必填，日期為 `YYYY-MM-DD`，角色留白預設 `agent`。
   匯入採**全有或全無**：任一列有誤即整批不寫入並逐列標示列號與原因。
   成功後畫面列出所有新帳號的初始密碼，**僅顯示一次**。
   既有帳號只更新資料、**不重設密碼**，因此本檔可重複上傳作為名冊同步之用。
3. **建立名單** — 名單為空時比對不會有任何結果，上線前務必先由洗防專責建立。

## 角色與權限

| 角色 | 權限 |
|---|---|
| 業務人員 `agent` | 只能建立與檢視**自己**的案件；送出後鎖定不可修改 |
| 單位主管 `supervisor` | 檢視與簽核**所屬通訊處**案件；同意高風險案件前須填列財富與資金來源 |
| 洗防專責 `compliance` | 全公司案件、名單維護、STR 標記、報表匯出、個資明文 |
| 內部稽核 `auditor` | 全公司案件唯讀、報表匯出、個資明文；不得維護名單或簽核 |
| 系統管理者 `admin` | 帳號與組織單位管理 |

## 部署（地端／私有雲）

```bash
cp .env.example .env
# 產生兩把金鑰後填入 .env
python -c "import secrets; print(secrets.token_urlsafe(48))"                      # AML_SECRET_KEY
python -c "import os,base64; print(base64.urlsafe_b64encode(os.urandom(32)).decode())"  # AML_PII_KEY
# 另設定 POSTGRES_PASSWORD 與 AML_BOOTSTRAP_ADMIN_PASSWORD

docker compose up -d --build
```

服務綁定 `127.0.0.1:8000`，**必須**在前方置放反向代理（Nginx／Caddy）並啟用 HTTPS，
同時限制存取來源。管理者首次登入後請清空 `.env` 中的 `AML_BOOTSTRAP_ADMIN_PASSWORD` 並重啟。

> ⚠️ **`AML_PII_KEY` 遺失，資料庫內已加密的姓名與身分證字號將永久無法還原。**
> 請依內控手冊 BIC05-02 之金鑰保管程序離線保存，並指定保管人與備援保管人。

### 資料庫結構變更（Alembic）

結構一律以遷移演進，**不使用 `create_all`**——它只會建立缺少的資料表，不會修改既有資料表，
上線後第一次新增欄位就會失效。案件紀錄須保存五年（範本第六點），資料庫不能重建。

```bash
alembic upgrade head                              # 套用到最新（部署時自動執行）
alembic revision --autogenerate -m "變更說明"      # 改完模型後產生遷移
alembic downgrade -1                              # 退回上一版
alembic current                                   # 查目前版本
```

改完 `app/models.py` 一定要產生對應的遷移。忘記的話 `test_migrations.py` 會失敗，
CI 就會擋下來——這比在正式環境遇到「程式要的欄位資料庫沒有」好得多。

應用程式啟動時會驗證資料庫是否為最新版本，**落後或未初始化即拒絕啟動**並指出該執行的指令。
容器的 `docker-entrypoint.sh` 會先跑 `alembic upgrade head` 再啟動服務。
（目前為單一應用容器，順序執行是安全的；若日後水平擴充，應改為獨立的遷移工作，
避免多個 worker 同時遷移互相競爭。）

## 資料庫

正式環境為 PostgreSQL 16，開發與測試預設為 SQLite。CI 兩者都跑
（`.github/workflows/aml-tests.yml` 的 matrix），因為兩者的行為差異只會在正式環境才顯現：

| 差異 | 後果 | 處理 |
|---|---|---|
| SQLite 取回的 datetime 無時區 | 與 `utcnow()` 比較拋 TypeError，帳號鎖定機制整個失效 | `models.as_aware()` 統一補時區 |
| SQLite 不強制 VARCHAR 長度 | 外部名單欄位過長時，PostgreSQL 拒絕寫入導致整批匯入失敗 | `screening._fit()` 依欄位上限截斷 |
| `LIKE` 大小寫敏感度不同 | 名單搜尋結果不一致 | 比對前一律正規化為大寫 |

已於 PostgreSQL 16 實跑驗證：遷移、136 項測試、示範資料、26,579 筆名單匯入、
瀏覽器操作流程、三種報表匯出，報表數字與 SQLite 完全一致。

效能參考（26,586 個對象／60,674 個名稱）：

| 作業 | SQLite | PostgreSQL |
|---|---|---|
| 名單匯入（每月一次） | 19 秒 | 81 秒 |
| 單次姓名比對（每次存檔） | 5 ms | 16 ms |

比對查詢在 PostgreSQL 上經 BitmapOr 走兩個索引，查詢本身 0.1 ms，
其餘為候選字串產生的時間；名單成長不會使其線性劣化。

## 報表

| 報表 | 用途 | 路徑 |
|---|---|---|
| 董事會定期報告 | 依 BIC06-03 九定期提報董事會，期間可自訂 | `/reports/board.xlsx` |
| 年度風險評估彙總表 | 向主管機關申報，版面比照 115 年格式 | `/reports/annual.xlsx` |
| 案件清冊 | 內部稽核與金融檢查調閱 | `/reports/register.xlsx` |

年度報表七個構面（地域、職業、自然人別、國籍、來源、產品、交易管道）的欄列位置與桶別權重
均以測試鎖定（`test_annual_workbook_matches_regulator_layout`）。產品風險同時輸出
**件數加權**與**保費金額加權**兩組分數——大額 OIU 單件即可顯著拉高保費加權風險，
這正是主管機關要求雙重加權的監理意義。

每次匯出都留存產出時間、產出人、筆數與內容 SHA-256，金檢時可據此證明報表未經事後修改。

## 申報時程

- **每年 4 月底前**：內部控制制度聲明書，由董事長、總經理、稽核主管、洗防專責主管聯名出具，
  提報董事會通過後依指定方式申報（範本第十二點第四款）。
- **每年**：風險評估報告更新並送主管機關備查（範本第十點第三款第四目）。
- **個案**：疑似洗錢交易經專責主管核定後 2 個營業日內向調查局申報（範本第九點）。

## 已知限制

- **名單比對不做模糊比對或音譯比對。** 外文姓名的音譯變體（如 Mohammed／Muhammad）
  需在名單中分別列出；來源清單本身已含大量別名，可涵蓋多數情形。
- **漢字公司名稱的詞序調換不會命中。** 例如名單上是「邦克台灣集團公司」，
  客戶寫「台灣邦克集團公司」不會被發現（漢字無空白，無法做詞彙子集比對）。
  部分相符與人工複核可涵蓋多數情形，但這是已知的漏網情境。
- **匯入來源的授權須自行確認。** 若名單檔中的歐盟清單係經第三方鏡像取得
  （如 OpenSanctions，授權為非商業使用），商業使用前應取得歐盟官方 FSD 授權，
  且對外不得標示為官方歐盟清單來源。
- 客戶姓名與身分證字號加密儲存，因此**無法以明文搜尋**。案件查詢改以案號、保單號碼或
  業務員姓名進行；同一客戶的歷次評估則透過身分證字號的盲索引串接。
- 年度報表「制裁名單、STR 與境外電匯件數」區塊的「平均風險分數」，原表為公式且未定義權重，
  系統輸出件數與占比並於該欄位加註說明。申報前請確認主管機關當年度的計算定義。

## 架構

```
app/
  scoring/          評分引擎（純函式，不碰資料庫，可完整單元測試）
    definitions/    版本化問卷定義（YAML）
  services/         評估流程、彙總、匯出、名單篩檢、稽核軌跡、行為異常偵測
  routers/          HTTP 路由（前台問卷、簽核、洗防後台、報表、管理）
  templates/        伺服器端樣板（無前端建置流程，稽核範圍不含 npm 依賴）
  static/           CSS 與自動儲存 JavaScript
tests/              56 項測試，每項對應一條法規要求或紙本檢核表規則
```

**自動儲存**：業務員每點選一個選項即立即寫入資料庫並回傳最新分數；文字欄位在停止輸入
900 毫秒後、或離開欄位時存檔。網路中斷時進入重試佇列，並在離開頁面前提示。
每一次作答變更都是新增一筆稽核軌跡（含前後選項與前後分數），不是覆蓋原紀錄。
